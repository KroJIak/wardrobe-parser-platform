# Дизайн инфраструктуры: устойчивость сервера

## Область применения

- Охватывает: лимиты памяти контейнеров, поведение при нехватке памяти, watchdog хоста, очистку диска.
- НЕ охватывает: масштабирование, балансировку, резервное копирование на второй площадке.
- Зависит от: `01-local-compose.md`, `02-hosted-dokploy-and-networking.md`, `03-operations-and-secrets.md`.

## Что показала практика

Хост витрины — 2 vCPU и 3.9 ГБ RAM. За 44 дня работы на нём четыре раза
срабатывал OOM killer, и все четыре раза виновником был процесс бэкенда:
он разрастался до 1.2–3.1 ГБ. Дальше цепочка выглядела так:

1. контейнер съедал память;
2. ядро убивало его;
3. Docker перезапускал контейнер, и он снова начинал есть память;
4. свободная память заканчивалась, процессы уходили в swap;
5. хост переставал отвечать даже на SSH — лечить это приходилось перезагрузкой.

Своп на таком хосте — ловушка: он не спасает хост, а делает его неотзывчивым.
Поэтому в схеме ниже своп для контейнеров запрещён, а нехватка памяти
разрешается быстрым убийством виновника на уровне cgroup.

## Лимиты памяти

Лимиты заданы в `docker-compose.yml` рядом с каждым сервисом, поэтому
одинаково применяются и локально, и на проде:

| Сервис | Лимит | Почему столько |
|--------|-------|----------------|
| postgres | 700M | кэш и соединения каталога на 23k товаров |
| redis | 300M | очереди пересчёта и кэш запросов |
| backend | 1300M | API витрины, тяжёлые выборки каталога |
| backend-worker | 1000M | фоновые пересчёты каталога |
| service | 900M | парсинг источников, обход страниц |
| frontend-site / frontend-admin | 150M | статика |

`memswap_limit` равен `mem_limit`: контейнер не уходит в своп, а получает
cgroup-OOM и перезапускается по `restart: unless-stopped`. Хост при этом
остаётся доступным.

Последний рубеж — сам Docker:

```
/etc/systemd/system/docker.service.d/10-docker-limits.conf
MemoryAccounting=yes
MemoryHigh=3200M
MemorySwapMax=0
TasksMax=4096
```

## Watchdog хоста

`/usr/local/bin/site-watchdog.sh` + таймер `site-watchdog.timer` проверяют
раз в минуту, отвечает ли бэкенд:

1. контейнер бэкенда в состоянии Running;
2. `GET /health` по адресу контейнера отвечает 200.

Проверка идёт по адресу контейнера: порты бэкенда наружу не публикуются,
поэтому `localhost:8000` на хосте не отвечает.

Восстановление двухступенчатое:

| Неудачных проверок | Действие |
|--------------------|----------|
| 1–2 | ждём: контейнер мог перезапускаться сам по `restart: unless-stopped` |
| 3 | мягкий шаг: контейнер запущен, но не отвечает — `docker restart` его |
| 10 | жёсткий шаг: перезапуск не помог — `systemctl reboot` |

Порог в десять минут выбран с запасом на деплой: сборка фронтенда занимает
до пятнадцати минут, и перезагрузка посреди неё только сорвала бы работу.
Поэтому при активной сборке (`docker build`, `buildkit`, `npm ci`,
`vite build`) перезагрузка откладывается.

Логи пишутся в `/var/log/site-watchdog.log`, состояние счётчика — в
`/var/lib/site-watchdog/failures`.

Все файлы лежат в `ops/` вместе с инструкцией по установке.

## Очистка диска

`docker-prune.timer` раз в сутки удаляет неиспользуемые образы, сборки и
тома старше недели. Без этого образы и слои buildkit копятся: за месяц
сборок диск вырос с 9.8 ГБ до 12 ГБ.

## Бэкап базы

`backup_db.sh` снимает две копии в `/var/backups/wardrobe`:

| Копия | Чем сделана | Размер | Восстановление |
|--------|-------------|--------|----------------|
| `wardrobe_db-<stamp>.dump` | `pg_dump -Fc` | ~14 МБ | `pg_restore` |
| `postgres_volume-<stamp>.tar.gz` | `pg_basebackup` | ~59 МБ | распаковать в каталог данных |

Обе копии согласованы и снимаются без остановки витрины: `pg_dump`
работает на согласованном снимке, а `pg_basebackup` копирует том вместе с
WAL штатным механизмом Postgres. Рядом лежат контрольные суммы sha256,
копии старше двух недель удаляются.

`backup-db.timer` запускает снятие копий раз в сутки.

## Чего пока нет

- Внешнего мониторинга с уведомлением. Watchdog живёт на том же хосте и
  не заметит его зависания — для этого нужен внешний сторож или проверка
  доступности с чужого IP.
- Алерта в Telegram: токена бота в окружении нет. Когда он появится,
  watchdog должен отправлять сообщение при перезагрузке и при
  недоступности витрины дольше двух проверок.

## Бан по IP блокирует и витрину

fail2ban банит адрес целиком, а не только порт 22. Из-за этого обрыв
SSH-соединения у администратора при нестабильной сети закрывал доступ к
самой витрине: сайт переставал открываться с того же IP.

Поэтому jail настроен мягко: пять попыток за десять минут, бан на полчаса,
а адреса, с которых идёт административный доступ, перечислены в
`ignoreip`. При смене адреса его нужно дописать — иначе хост снова
окажется недоступен извне.

Проверить, не заблокирован ли адрес:

```bash
fail2ban-client status sshd | grep "Banned IP list"
fail2ban-client set sshd unbanip <ip>
```
