# 01. Admin Scenarios

> [!info]
> Ниже перечислены **сценарии продукта**, которые новая БД обязана поддерживать.
> Это не копия текущей схемы. Это смысловая база для проектирования.

## 1. Сценарии вкладки `Товары`

### 1.1. Админ просматривает каталог

Админ должен иметь возможность:

- видеть список товаров;
- искать по названию, ссылке, handle и текстовым атрибутам;
- фильтровать по источнику, дизайнеру, категории, статусу;
- видеть коммерческий режим товара: `В наличии` или `Под заказ`;
- открывать карточку товара;
- видеть итоговую цену и исходную цену;
- видеть внутренние категории и витринные статусы.

Из этого следуют сущности:

- `products`
- `product_listings`
- `designers`
- `sources`

### 1.2. Админ меняет состояние товара

Админ меняет:

- `visible/hidden`;
- режим товара `В наличии / Под заказ` как отдельную ось, а не как status;
- `gender` товара, в том числе массово;
- ручную рублевую цену товара;
- ручную рублевую скидку товара;
- ручное название;
- ручное текстовое описание;
- ручное HTML-описание;
- изображения.

Из этого следуют отдельные данные:

- catalog-level статус видимости;
- catalog-level режим доступности;
- `gender` как редактируемый классификационный атрибут товара;
- отдельная сущность ручной рублевой цены товара;
- отдельная таблица представления товара;
- отдельная таблица витринных фото-стеков по listing;
- текстовое и HTML-описание товара должны храниться раздельно;
- публичное описание товара должно выбираться по режиму источника;
- display-title и итоговое описание должны вычисляться как `manual layer -> primary listing`;
- невозможность хранить ручной presentation-слой прямо в source listing.

### 1.3. Админ создает ручной товар

Админ может:

- создать товар без parser source;
- задать название, описание, дизайнера, вес, изображения и варианты;
- опционально привязать его к source-ссылке;
- назначить избранные категории.

Из этого следуют правила:

- ручной товар и source-imported товар должны жить в одной доменной модели `products`;
- но происхождение записи должно быть выражено явно;
- ручной товар не должен требовать fake-source как основного способа существования;
- базовые `title/description` ручного товара должны жить в manual listing, а не в отдельном каноническом дубле;
- если в runtime остается специальный `manual source`, он должен быть только техническим профилем ingest-режима, а не смысловым владельцем товара.

### 1.4. Админ редактирует ручной товар

Админ может:

- менять поля товара;
- менять `gender`;
- менять режим `В наличии / Под заказ`;
- ставить ручную рублевую цену;
- снимать ручную рублевую цену и возвращать derived pricing;
- выставлять скидку через новый рублевый ценник с сохранением предыдущего рублевого;
- менять изображения;
- менять варианты;
- включать или отключать bind с внешним source;
- удалять товар.

Из этого следуют правила:

- manual mode должен быть естественным состоянием listing, а не побочным сценарием;
- ручные изображения и ручные варианты не должны притворяться source lineage.
- ручной вес товара должен жить на уровне `products`, а не внутри source listing.

### 1.6. Админ управляет ручной рублевой ценой

Админ должен иметь возможность:

- выставить товару ручную цену в рублях;
- изменить ее у любого товара;
- отключить для этого товара derived pricing от source + формулы;
- вернуть товар обратно на derived pricing;
- создать скидку, сохранив прежнюю рублевую цену как зачеркнутую.

Из этого следует:

- ручная цена не должна жить ни в `products`, ни в `product_listings`;
- ручная цена не должна перетирать source price;
- скидка не должна быть отдельным status или отдельным видом товара;
- ручная рублевая цена и ручная старая рублевая цена должны жить в отдельной сущности товара.

### 1.5. Админ массово меняет `gender`

Админ должен иметь возможность:

- менять `gender` сразу у множества товаров;
- исправлять ошибочную автоматическую классификацию;
- делать это без переписывания source snapshot.

Из этого следует:

- `gender` является собственностью `products`, а не `product_listings`;
- source-слой может участвовать в вычислении `gender`, но не является его окончательным владельцем в новой схеме.

## 2. Сценарии вкладки `Источники`

### 2.1. Админ управляет source-профилем

Админ может:

- включать или выключать источник;
- включать или выключать sync;
- скрывать auto-added товары источника;
- выбирать режим описания источника: `hidden / text / html`;
- выключать изображения этого источника;
- запускать sync;
- отменять sync.

Из этого следует:

- `sources` это отдельный bounded context;
- у source есть настройки ingest и display policy;
- эти настройки не принадлежат товару.

### 2.2. Админ меняет описание синхронизированного товара

Админ может:

- открыть синхронизированный товар;
- поменять текстовое описание;
- позже включить у источника HTML-режим описания;
- после этого поменять HTML-описание того же товара;
- не потерять ни текстовую, ни HTML-версию.

Из этого следует:

- ручное текстовое описание и ручное HTML-описание должны храниться отдельно;
- source-layer не должен терять свои `source_description_text` и `source_description_html`;
- открытое API должно возвращать одно поле `description`, а не два;
- значение `description` должно выбираться по display-режиму источника.

### 2.3. Админ видит товары источника

Значит БД должна поддерживать:

- получение всех listing одного source;
- связь товара каталога с несколькими listing одного или нескольких source;
- вычисление source counts без нестабильного JSON lineage;
- source-фильтрацию через реальные listing-связи, а не только через поле `product.source_id`.

## 3. Сценарии вкладки `Дедупликация`

Админ может:

- видеть кандидатов на дубль;
- отклонять дубль;
- merge нескольких товаров в один витринный товар.

Из этого следуют правила:

- дедуп — это отдельный контур решений, а не “особый вид товара”;
- витринный `product` должен уметь собираться из нескольких source-listing;
- source listing должен оставаться атомарной sync-сущностью;
- variants и source-фото должны оставаться привязанными к своему listing;
- merge должен создавать новый активный `product` из плоского union member-listing входных товаров;
- старые входные `product` должны переводиться в `merged`;
- журнал решений должен быть отдельной сущностью.

## 4. Сценарии вкладки `Дизайнеры`

Админ может:

- включать или выключать исходный бренд;
- переименовывать его в финальное имя дизайнера;
- объединять несколько исходных брендов под одного публичного дизайнера;
- задавать единое описание дизайнера;
- создавать и удалять дизайнеров каталога.

Из этого следуют сущности:

- `designers`
- `designer_source_names`

И следуют ограничения:

- source brand и финальный дизайнер — не одно и то же;
- один дизайнер может объединять много исходных source brand;
- имя, slug и описание должны принадлежать дизайнеру каталога, а не отдельной “странице”.

## 5. Сценарии вкладки `Фильтры, Категории и витрины`

Admin UI уже формулирует целевой продуктовый смысл:

- есть локальные категории товаров;
- есть фильтры;
- есть мультифильтры;
- есть кастомные каталоги;
- есть системные категории верхней витрины;
- есть attachments фильтров и кастомных каталогов к витринным категориям;
- есть скрытие узлов внутри attachment;
- есть designer directory;
- есть ручные товары внутри rule-based сущностей.

Из этого следуют отдельные сущности:

- `filters`
- `filter_nodes`
- `filter_local_category_keywords`
- `filter_title_keywords`
- `filter_manual_products`
- `custom_catalogs`
- `custom_catalog_products`
- `showcase_categories`
- `showcase_category_attachments`
- `showcase_category_attachment_hidden_nodes`

И отдельное правило:

- статус товара не должен быть ключевым словом таксономии;
- filter-правила должны опираться на классификацию товара, а не на его оперативное availability/visibility состояние;
- кастомный каталог должен уметь хранить не только имя, но и описание для витрины;
- `showcase_categories` — это фиксированный seeded-справочник, а не CRUD-сущность админки.

## 6. Сценарии вкладки `Ценообразование`

Админ может:

- редактировать глобальные pricing settings;
- редактировать suppliers;
- редактировать тарифы;
- управлять валютными и пороговыми правилами;
- видеть pricing example.

Значит нужны:

- `suppliers`
- `supplier_shipping_rates`
- `pricing_settings`
- при необходимости нормализованные child-таблицы для диапазонов, а не JSON-поля.

## 7. Сценарии вкладки `Вес`

Админ управляет:

- правилами веса;
- ключевыми словами для правил веса.

Отсюда:

- `weight_rules`
- `weight_rule_keywords`

И отдельное правило:

- пересчет веса по ключевым словам не должен синхронно переписывать весь каталог после каждой мелкой правки;
- изменение правила веса должно запускать фоновый пересчет затронутых товаров или отдельную batch-задачу;
- итоговый вес товара должен храниться отдельно от source-веса и от самого правила.

## 8. Сценарии `Настройки` и auth

Админ может:

- управлять пользователями;
- управлять ролями;
- менять admin-ui настройки;
- переносить настройки.

Значит нужны:

- `admin_users`
- `admin_roles`
- `admin_role_permissions`
- `admin_ui_settings`

## 9. Главные инварианты, вытекающие из admin-сценариев

> [!warning]
> Один и тот же объект не должен одновременно быть:
> - source listing,
> - catalog product,
> - container для ручного presentation-слоя.

> [!warning]
> Merge не создает отдельный “тип товара”.
> Это обычный `product` с жизненным состоянием `merged` у входных записей и новым активным `product` как результатом решения.

> [!warning]
> Source attributes и admin presentation-данные должны храниться отдельно.

> [!warning]
> Галерея товара является двухслойной:
> - source images
> - manual/display overlay

> [!warning]
> Дизайнер как витринная сущность и исходное название бренда в источнике — разные сущности.

> [!warning]
> Фильтр, мультифильтр, кастомный каталог и витринная категория — разные типы объектов, а не одна таблица с булевыми флагами.
